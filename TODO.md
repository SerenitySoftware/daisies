# TODO

Daisies is a small, predictable wrapper for safely reading unreliable nested Python data. New features should directly strengthen that promise without turning the library into a query language, serializer, schema system, or general-purpose data toolkit.

## Core safe navigation

- [x] **Distinguish missing values from explicit `None`.** Introduce an internal missing sentinel so a path that did not resolve is different from a key or index whose value is actually `None`. Keep the public, null-tolerant behavior intact while making `.exists()` return `True` for every resolved value—including `None`, `0`, `False`, `""`, and empty containers—and `.is_missing()` return `True` only when navigation failed.

- [x] **`.fallback(...)` for multi-source defaults.** Express “try this path, then that path, then a literal default” fluently: `data.user.email.fallback(data.contact.email).fallback("noreply@example.com")`. Return the current Chain when it resolved, even to an explicit `None`; otherwise return the Chain-wrapped fallback. Accept either another `Chain` or a plain value, never raise, and remain wrapped so navigation can continue.

- [x] **`.pluck(*keys)` for whitelist projection.** Return a Chain-wrapped dictionary containing only the requested keys from the current mapping, silently skipping absent keys. Missing or non-mapping values produce an empty wrapped dictionary. This should compose directly with `.dict()` and `.json()` for small outbound payloads without becoming a general query API.

- [x] **`.value(type_)` can still raise when coercion fails.** *(Observed 2026-09-15 by the TODO routine on `master` at 76b6454; fixed 2026-09-16.)* The README promised “Coercion failures fall back too — never raises”, but `Chain.value()` caught only `(TypeError, ValueError)`, so `decimal.InvalidOperation` — an `ArithmeticError` — escaped and `Chain({"amt": "abc"}).amt.value(Decimal, default=Decimal("0"))` raised instead of returning the default. The except clause now covers the families a coercion callable raises when the value is the wrong shape for it (`TypeError`, `ValueError`, `ArithmeticError`, `LookupError`, `AttributeError`), while a genuine bug inside a coercion callable still propagates. Note this also closes the final clause of the backlog item below; the rest of that item — iteration, `len()`, and `in` on a missing node — is still open and unpromoted.

- [x] **`[...]` on the wrong kind of container leaked `TypeError`.** *(Observed 2026-09-17 by the TODO routine on `master` at 685c472; fixed 2026-09-17.)* `Chain.__getitem__` caught only `(KeyError, IndexError)`, so a string key on a list (`data.users["name"]`), a string key on a string (`data.title["name"]`), a float index, or an unhashable key raised `TypeError` straight out of the chain, while the dotted form of the same path (`data.users.name`) resolved to `None`. That narrow clause dated from the original rename commit (`2b158ef`) and was never revisited when `_COERCION_FAILURES` grew to absorb exactly this "vendor sent a different shape" family. The except now covers `TypeError` as well and records the hop as missing, so `.trace()` and `on_missing` name it and strict mode raises `MissingPathError` on unwrap like any other miss. Ordinary bracket access — dict keys, list indices, slices, string indices — is unchanged.

- [x] **The README said an explicit `None` "reads as missing".** *(Observed 2026-09-18 by the TODO routine on `master` at 3c05fae; fixed 2026-09-18.)* The parenthetical closing the `.exists()`/`.is_missing()` section — "A key set literally to `None` reads as missing, since a missing hop is itself `None`" — was written for 0.3.0 (`b37f74a`, 2026-07-09), before the missing sentinel at the top of this section made `.exists()` true for every resolved value. Shipping that item should have deleted the line and didn't, so the README contradicted its own `data.user.nickname.exists()  # True: the key is present` eight paragraphs earlier, its `.trace()` section, and the cookbook. A reader trusting it would reach for `.is_missing()` to catch a vendor's explicit nulls and catch none of them. Verified against `master`: `Chain({"nickname": None}).nickname.exists()` is `True` and `.is_missing()` is `False`. The prose now says an explicitly nulled key exists and points at `.exists()`/`.fallback()` for telling the two apart; `test_readme.py::test_exists_and_is_missing` — the one claim in that section it had no assertion for, which is why the drift survived — now covers it. Behaviour unchanged; documentation only.

- [x] **`.json()` raised `TypeError` on a dict key it would have stringified as a value.** *(Observed 2026-09-21 by the TODO routine on `master` at fd2d283; fixed 2026-09-21.)* `Chain.json()` sets `default=str` so an unserializable *value* degrades to its string form, but `json.dumps` never consults `default=` for **keys**: it accepts only `str`, `int`, `float`, `bool`, and `None` and raises `TypeError` on anything else. So `Chain({"when": date(2026, 7, 9)}).json()` gave `'{"when": "2026-07-09"}'` while `Chain({date(2026, 7, 9): 12}).json()` raised — the same type, the same method, opposite behaviour depending on which side of the colon it sat, contradicting the README's "degrades to its string form instead of raising `TypeError`" and the method's own "Never raises". It bit at any depth (`{"by_day": [{date(...): 3}]}`) and applied to every key type you get from grouping records in Python rather than from parsing JSON — `date`, `Decimal`, `UUID`, tuple. The only escape was `skipkeys=True`, which silently *drops* the field. `json()` now retries through `_json_safe()` when `dumps` refuses, stringifying keys outside the allowed set and degrading self-referential containers (the `ValueError` `default=` cannot intercept either) to their string form; the happy path is untouched and pays nothing, an explicit `skipkeys=True` still wins, and a caller's own `default=` still sees the values it would have. `test_serialization.py` covers keys at the root and nested, ordinary keys left alone, `skipkeys`, cycles, and `default=` on the repair path; `test_readme.py::test_json_stringifies_unserializable_keys` pins the new README claim.

- [x] **An object with a data attribute named `items` raised on every hop.** *(Observed 2026-09-22 by the TODO routine on `master` at 59f40c3; fixed 2026-09-22.)* `sniff.isdictlike()` read any object that merely *had* an `items` attribute as a mapping, so a cart, an order, or a page of results — objects whose most ordinary field is literally called `items` — was navigated with `wrapped.get(...)` and raised `AttributeError: 'Cart' object has no attribute 'get'` on **every** attribute access, including `Chain({"cart": cart}).cart.id`. `.dict()` raised `TypeError: 'Cart' object is not iterable` against its own "returns an empty dict when the wrapped value isn't dict-like", and `.tree()` raised `object of type 'Cart' has no len()` against its "never raises on odd input". A data attribute named `keys` or `values` failed the other way: `Chain(index).keys` handed back the view proxy instead of the field, contradicting the README's "A field literally named `keys`/`values`/`items` still wins on attribute access". `isdictlike()` now requires `items` to be *callable* — which is what the duck-type was always for, a mapping that isn't a `Mapping` subclass — and `Chain.__getattr__` lets a real attribute win over the `keys`/`values`/`items` proxies on the object path exactly as a data key already did on the dict path, so the proxies still answer `[]` for a value that has no such attribute. The README now says the rule covers plain objects; `test_sniffs.py`, `test_navigation.py`, `test_iterables.py`, and `test_readme.py::test_an_objects_own_items_attribute_wins_over_the_view` cover it.

- [x] **Arithmetic with a missing field on the right raised `TypeError`.** *(Observed 2026-09-23 by the TODO routine on `master` at 4bfff2b; fixed 2026-09-23.)* The README's arithmetic section promises operators coerce `None` to zero "to ensure that you don't raise errors", and they did — for a missing field on the *left*, or a Chain on the right of a plain number. Chain-to-Chain, the form the README teaches (`data.price * data.quantity`), was only half-covered: `data.price + data.missing` raised `unsupported operand type(s) for +: 'int' and 'NoneType'`, as did `-` and `**`, while `100 + data.missing` calmly gave `100`; and `data.missing - data.discount` raised `bad operand type for unary -: 'Chain'` because `__sub__` negated `other` before unwrapping it (all reproduced on `master`). `__add__`, `__sub__`, and `__pow__` now unwrap the right-hand side first and treat `None` there exactly as the reflected operators already treat it on the left — `x + missing` and `x - missing` are `x`, `x ** missing` is `0`, `missing - y` is `-y` — so which side of the operator a missing field lands on no longer decides whether the expression raises. `*`, `/`, `//`, and `%` already answered `0`. A present value of the wrong type still raises (that is the backlog item below). `test_operators.py` and `test_readme.py::test_arithmetic` cover it.

- [ ] **A duck-typed mapping that offers only `items()` still raises on every hop.** *(Observed 2026-09-22 by the TODO routine on `master` at 59f40c3; the other half of the item above, deliberately left as-is by that fix.)* After the fix above, `isdictlike()` accepts anything with a callable `items`, but `Chain` then calls three *other* things on it: `wrapped.get(name, _MISSING)` in `__getattr__`, `dict(wrapped)` in `.dict()`, and `len(value)` in `_describe_node` for `.tree()`. A class that defines `items()` and nothing else — reproduced with `class Row: def items(self): return self._d.items()` — raises `AttributeError: 'Row' object has no attribute 'get'`, `TypeError: 'Row' object is not iterable`, and `TypeError: object of type 'Row' has no len()` respectively. A `Mapping` subclass or anything with the full read protocol (`get`, `keys`, `__getitem__`, `__len__`) is unaffected, which is every mapping in the standard library and every one the test suite has. **Waits on Jordan:** the two fixes point opposite ways. Tightening `isdictlike()` further — demanding the whole read protocol, not just `items` — makes such an object navigate as a plain object, so nothing raises but `.dict()` silently answers `{}` and its fields read as missing. Reading it through `items()` instead preserves the data but means `.dict()` and `.tree()` stop going through the mapping protocol for everyone. Narrow either way: it needs a hand-written partial mapping, not a shape any vendor's JSON can produce.

- [ ] **`.json()`'s repair path caps out ~5x shallower than `json.dumps` itself.** *(Observed 2026-09-21 by the TODO routine on `master` at 33f79f2, in the fix shipped immediately above.)* `_json_safe()` is a plain recursive walk, so it spends one Python frame per nesting level and hits `RecursionError` at a depth of ~1000 (the default `sys.getrecursionlimit()`), while `json.dumps`'s C encoder serializes the same shape to ~5000 and only raises at ~20000. Measured on `master`: a 2000-deep dict serializes fine through `Chain(deep).json()`, but `Chain({date(2026, 7, 9): "x", "d": deep}).json()` raises `RecursionError`. No payload that used to work regressed — the repair only runs after `dumps` has already refused, so that data raised `TypeError` before — but a promise that reads "never raises" should not have a ceiling five times lower than the encoder it wraps. **Waits on Jordan:** raising the ceiling means rewriting the walk with an explicit stack, which trades away the readability of a helper whose whole appeal is that you can see what it does in one screen, for a case that needs ~900-deep nesting *and* an already-refused key. Worth doing only if that trade is one he wants; there is no depth at which *nothing* raises, since the stdlib gives out too.

- [ ] **`.json(sort_keys=True)` still raises on a dict with mixed key types.** *(Observed 2026-09-21 by the TODO routine on `master` at 33f79f2.)* `Chain({1: "a", "b": 2}).json(sort_keys=True)` raises `TypeError: '<' not supported between instances of 'str' and 'int'` — `dumps` sorts the keys before rendering them, and `int` and `str` do not compare. The repair path added above does not catch it: both keys are types `dumps` accepts, so `_json_safe()` leaves them alone and the retry raises identically. Unlike the key case it fixes, this one is provoked by the caller's own `sort_keys=True` rather than by the data alone, and `dumps` renders *every* key as a string anyway (`{1: "a"}` → `'{"1": "a"}'`), so sorting on the rendered form would be faithful for `str`/`int`/`float` keys. **Waits on Jordan:** `True` and `None` render as `true`/`null` but `str()` to `True`/`None`, so "sort by the rendered key" needs a rule for those two before it can be built. Narrow either way: it needs mixed key types *and* an explicit `sort_keys=True`.

## Debugging safe navigation

- [x] **`.trace()` for explaining a missing result.** Record and expose the navigation path and the first hop that failed, so `chain.user.address.city.trace()` can explain whether `user`, `address`, or `city` was missing. Keep the result compact and useful in logs, preserve the distinction between a missing hop and an explicit `None`, and avoid changing normal navigation behavior.

- [x] **Strict mode for tests and development.** *(PM rec, August 2026)* Never raising is the library's central promise and also its one blind spot: a *typo* is indistinguishable from a genuinely absent field, so `data.user.emial` silently resolves to `None` and ships. Add an opt-in strict mode — `Chain(raw, strict=True)` plus a `daisies.strict()` context manager for code that doesn't own the wrapping — that raises on a missing hop while leaving every other behavior identical, so the same navigation code can run strict under pytest/CI and tolerant in production. Fail-fast on your own mistakes, null-tolerance on the vendor's. Builds directly on the missing sentinel already added above; strictness must be carried through `__getattr__`/`__getitem__` onto derived Chains, and `.fallback()`/`.value(default=...)` must stay non-raising (an explicit default *is* handling the absence). Distinct from `.trace()` — that explains a miss after the fact, this refuses to let one pass silently in the first place.

- [x] **A missing-path observer hook.** *(PM rec, August 2026)* `daisies.on_missing(callback)` — a process-wide (or context-scoped) callback fired whenever navigation fails, receiving the path that missed. Turns the library's silent degradation into a production signal: counting or logging missing paths is how you find out *which fields a third party stopped sending, and when* — the exact failure Daisies exists to survive but currently hides. Keep it strictly observational (never alters resolution, never raises out of the callback, near-zero cost when unset) and share the recording plumbing with `.trace()` and strict mode above, since all three key off the same failed hop.
- [x] **Tab completion for wrapped keys (`__dir__`).** *(PM rec, September 2026; promoted 2026-09-25; shipped 2026-09-25 — `Chain.__dir__` also leaves out Python keywords such as `"class"`, which pass `isidentifier()` but can't follow a dot; `test_dir.py` covers it.)* Define `Chain.__dir__` so `dir(data.user)` — and therefore `data.user.<TAB>` in the stdlib REPL, IPython, and Jupyter — lists the wrapped dict's identifier-shaped keys (or `dir()` of a wrapped object) alongside the Chain methods. Introspection only: navigation, `_navigate`, and the slots are untouched. Verified 2026-09-25 on `master` at 70d2cba: `rlcompleter.Completer.attr_matches("data.user.na")` returns `[]` today, and a scratch subclass carrying exactly that `__dir__` makes the key complete while filtering `"jeffrey-epstein"`. Full case in the backlog under [PM recs, 2026-09-25](#pm-recs-2026-09-25).
